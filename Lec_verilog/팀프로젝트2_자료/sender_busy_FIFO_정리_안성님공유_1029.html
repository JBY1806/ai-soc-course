안성님 01_UART_DECODER.pdf (05:31) 트러블슈팅을 보고 정리. 숫자는 9600 bps · 100 MHz 기준 계산값이고, 6 장 자원만 합성 실측. 정리 : 정보윤 (계산 · 합성 · 그림은 작성).

0. 결론

  • send_busy 는 "sender 가 글자를 TX FIFO 에 다 넣을 때까지" 만 1 (1 클럭에 1 글자). 선으로 PC 에 나가는 13 ms 는 TX FIFO · UART_TX 가 따로 처리 → 13 글자 응답이면 busy ≈ 130 ns.
  • PDF 의 busy 11 ms 는 "선으로 다 나갈 때까지 busy" 로 본 최악 가정. 실제로 busy 가 길어지는 건 TX FIFO 가 응답보다 작을 때 뿐.
  • 그래서 제 쪽 TX FIFO 를 가장 긴 응답보다 크게 (64 칸) 잡으면, 지금 디코더 구조 (busy 중 pop 멈춤) + RX FIFO 16 그대로 둬도 RX 가 넘칠 일이 없음.

3. busy 가 길어지는 경우 = TX FIFO 가 꽉 찰 때

busy ≈ (응답 글자 수 − TX FIFO 빈칸 − 1) × 1.04 ms. 0 이하면 글자 수 × 10 ns. (−1 = UART_TX 가 처음에 바로 꺼내 가는 한 글자)

/get 을 연달아 쳐도 : /get sw_hm 은 10 글자라 들어오는 데만 ≈ 10.4 ms → 두 번째 /get 이 완성될 때 앞 응답은 2 ~ 3 글자만 남아 있음 → TX 16 칸이면 busy ≈ 130 ns 그대로.

4. busy 와 RX FIFO (지금 구조 = busy 중 pop 멈춤)

busy 동안 들어올 수 있는 글자 ≈ busy ÷ 1.04 ms (PC 가 쉬지 않고 보내는 최악). 이게 RX FIFO 빈칸보다 많으면 넘친 글자가 버려져 명령이 깨짐 (PDF 3 쪽 sw_/g).

7. /auto 제안

/auto 뒤 인자로 보낼 것 고르기 : /auto sw (스톱워치만) · /auto dist (거리만) · /auto all (전부) · /auto off. all 이면 U_CONTROL 이 종류마다 send_sel 바꿔서 send_go 를 한 번씩 (send_busy 0 될 때마다). 5 종 54 글자 (예시 형식) 면 1 초 중 ≈ 56 ms.

응답 형식 제안 (sender) : 스톱워치 · 시계 · 타이머 12:34:56.78 (11 글자) · 거리 123cm (5) · 온습도 45%25C (6, 정수만) · ERROR (5), 모두 끝에 줄바꿈 CR LF (2 글자). → 가장 긴 응답 13 글자, 5 종 전부 54 글자 → TX FIFO 64 칸 (자원 차이가 작아 all 여부와 상관없이 64 로).

8. 확인하고 싶은 것

  1. 명령 목록 표 (명령마다 인자 · 뜻 — sw_hm, sw_ms, /btn L 등), 특히 응답이 필요한 명령 중 가장 짧은 것
  2. byte enable = 인자 5 칸 중 진짜 글자인 칸 표시 (R 이면 첫 칸만 1) 맞는지
  3. 인자가 5 글자보다 길게 들어오면 어떻게 처리하는지
  4. /mod · /btn 같은 명령에도 응답 (OK 등) 을 보낼지 — 보내면 send_go 가 필요한 명령이 늘어남
