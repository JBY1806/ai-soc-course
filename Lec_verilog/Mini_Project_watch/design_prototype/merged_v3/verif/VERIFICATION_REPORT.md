## 3. 소견 (설계에 대해 알아야 할 것)

### F1. [DEVIATION · 팀 결정 필요] 스톱워치 CU 가 RUN 중에도 L · U 를 받는다
- **(10/16 14:50 해결)** 정보윤 결정: RUN 중 L · U 무시. merged_v3 `src` 와 팀 저장소 `boyun/merged_v4` (커밋 f39f97e) 의 CU 두 곳 수정, SV 모델 · Top 지시형 T17 도 새 사양으로 바꿈. 재검증 모두 MISMATCH 0, 단위 TB DEVIATION 4 → 1 (STOP 에서 R+L 같은 클럭만 남음). 아래는 수정 전 기록.
- 팀 `stopwatch_control_unit`: `clear = btn_clear`(상태 무관), `if (btn_mode) mode_reg <= ~mode_reg`(상태 무관).
- 9일차 판서 FSM(STOP · RUN · CLEAR · MODE): RUN 에서는 R(정지)만 받고 L · U 는 무시.
- 보이는 동작: 달리는 중 L → 0 으로 지워지고 **계속 달림**(랩도 풀림). 달리는 중 U → 방향이 즉시 뒤집힘. STOP 에서 R+L 같은 클럭 → RUN 하면서 0 으로.
- 어느 쪽이 "맞다"가 아니라 **발표 때 설명할 사양을 하나로 정해야** 한다. 판서대로 할 거면 CU 두 줄(`clear`, `mode` 갱신을 STOP 에서만)만 바꾸면 되고, 그러면 SV 모델도 두 줄 바뀐다(모델은 지금 팀 동작을 기준으로 짜 두었음).

### F2. [정확도] 공용 100 Hz tick → 시작할 때마다 최대 10 ms 오차
- tick_gen 하나를 셋이 나눠 쓰고 각 데이터패스는 `tick & run` 으로 거른다 → 시작 순간이 tick 위상과 무관하므로 첫 칸이 0~10 ms 사이 아무 때나 올라간다.
- 측정: T17 시작 → 첫 증가 지연 최대 1,010 ns(축소, = 1 tick + 1클럭), T11 타이머 1분 = 5,999,610 ns(축소 6,000,000 기대 → 최대 1 tick 짧음), T15 10초 = 999,610 ns.
- 실제 시간으로: 스톱워치 시작/정지 한 번마다 ±10 ms, 타이머 알람 최대 10 ms 빠름. 수업 구조(데이터패스마다 tick_gen + clear 로 위상 재시작)는 이 오차가 없다. PPA(카운터 절약)와 정확도의 트레이드오프 — 발표에서 수치와 함께 말하면 소재가 된다. 없애려면 start 때 tick 카운터를 0 으로 맞추는 신호(clear)를 공용 tick_gen 에 넣으면 되지만 그러면 시계 tick 위상도 같이 흔들리므로, 스톱워치 · 타이머만 쓰는 tick_gen 을 하나 더 두는 식이 안전하다.

### F3. [TS-40] 디바운서: 누른 채 0.3 ms 끊김 → 2번 인식, 리셋 중 누르고 있던 버튼 → 리셋 뒤 1번 더 인식
- 8칸 AND 라 0 하나에 바로 꺼지고 2 ms 뒤 다시 켜짐. 히스테리시스(모두 0 이어야 꺼짐)로 막을 수 있음(`design_prototype\build_2khz_hyst`). 리셋 재인식은 "리셋 = 다시 시작"으로 보면 정상.

### F4. [동시 입력 규칙 — 확인됨, 참고] 
- 시계 설정: sw2 내림 > L > R, U > D (전수 검사로 확정). L+R+U+D 를 한 번에 누르면 U 는 **누른 클럭의 자리**에 적용되고 그다음 클럭에 자리가 옮겨진다(T13).
- 타이머 SET: L > U > R > D. 0 에서 L+U 를 같이 누르면 L 가지가 먼저라 U 도 무시됨(아무 일 없음) — 사람이 그럴 일은 없지만 사양에 적어 둘 것.
- 펄스가 나오는 바로 그 클럭에 sw0 를 바꾸면 펄스는 **바뀐 쪽 하나에만** 들어간다(둘 다 X, 아무도 X 없음)(T14).

### F5. [참고] 점(dp)과 점멸의 위상
- `dot` 모듈: msec ≥ 50 이면 1 = **점 꺼짐**. 즉 점은 msec 0~49 에 켜지고, 설정 자리 점멸은 msec 50~99 에 꺼진다(점과 숫자가 번갈아). 수업 fnd_controller 와 같은 극성. 타이머가 멈춰 있을 때(msec = 0)는 점이 **계속 켜진** 상태.
- 검증 TB 두 개(fnd 단위, SV 모델)가 처음에 이 극성을 거꾸로 기대해 각각 160건 · 24,990건 불일치를 냈고, 설계를 확인한 뒤 TB 를 고쳤다(설계는 맞음).

### F6. [견고성 · 보드에서만 보이는 것] 스위치 · rst 는 동기화 없이 바로 들어간다
- sw0~sw4 가 튀는 동안(수 ms) 화면 선택이 왔다 갔다 → 사용자가 본 "스위치 만질 때 숫자가 순간 튐". 버튼 펄스가 그 사이에 오면 엉뚱한 쪽으로 갈 수 있음(펄스는 1클럭이라 확률 낮음). rst(btnC) 해제도 비동기. 시뮬에서는 스위치가 깨끗해서 안 보인다. 스위치용 2단 동기화 + 간단한 디바운스를 권함(필수 아님).

### F7. [구조] 4 kHz 1클럭 펄스를 클럭으로 씀
- `btn_debounce` 시프트와 `counter8` 이 `posedge clk_remake`. 동작은 맞지만 파생 클럭이라 STA 경고(수업 구조와 같음). enable 방식(`if (tick)`)으로 바꾸면 경고 0 (PPA After 판에서 확인).

### F10. [검증 도구 한계 — 확인됨] xsim 2022.2 는 동시 어서션(assert property)을 실행하지 않는다

## 7. Verilog 지시형 vs SystemVerilog 랜덤 — 결과가 다른가?

**같은 설계 · 같은 시뮬레이터에서 "설계의 동작"은 똑같다.** 다른 것은 *무엇을 찾아내느냐*와 *얼마나 쓰기 쉬우냐*다.

| | Verilog 지시형 (HW2 식) | SystemVerilog 랜덤 + 모델 |
|---|---|---|
| 자극 | 사람이 순서를 씀 (T1~T21) | 클래스 제약으로 자동 생성(길이 · 간격 · 동시 · 튐 · 스위치 · 리셋) — 사람이 생각 못 한 순서가 나옴 |
| 기대값 | 시나리오마다 손으로 적음 → 틀리기 쉬움(4장 11건 중 9건이 여기) | 모델 하나를 쓰면 **매 클럭** 자동 비교 → 시나리오 늘려도 기대값 작업 없음 |
| 잡기 쉬운 것 | 정확한 시각 · 주기 · 지연 측정(F2 수치), 사양 차이(F1 은 "판서대로면 이래야" 를 적어야 보임) | 상태 조합의 구석(동시 입력 × 상태 × 화면), 리셋이 아무 때나 오는 경우, 긴 랜덤 시퀀스 |
| 못 잡는 것 | 안 적은 시나리오 | **모델이 DUT 와 같은 가정을 공유하면 둘 다 틀려도 통과**(점 극성 사건이 그 예 — 모델이 틀렸는데 설계와 같이 틀렸다면 못 잡았을 것). tick 주기 같은 "시간" 은 모델이 DUT 의 tick 을 관찰하므로 못 봄(변이 M22 · M23) |
| 커버리지 | 없음(시나리오 목록이 곧 커버리지) | 커버그룹이 "무엇을 지나갔나"를 숫자로 보여 줌 — 타이머 59:59 상한은 랜덤으로 못 가서 지시형이 필요하다는 것도 숫자로 드러남 |
| 수업 범위 | 배운 문법만 | class · rand · constraint · covergroup · assert property 등 미배운 문법(4번째 과목 SV/UVM 에서 배움). 지금 과제 TB 는 Verilog 식이 맞음 |

둘은 경쟁이 아니라 **층**이다: 단위(전수) → 지시형(시나리오 · 시간 측정) → 랜덤(구석 · 조합). 이번에 bug 0 이라는 결론은 세 층이 서로 다른 방법으로 같은 답을 냈기 때문에 믿을 만하다.
