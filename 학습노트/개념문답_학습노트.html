    A. 하드웨어

    라즈베리파이가 뭐야? CPU야?
    CPU가 아니라, 손바닥만 한 컴퓨터 한 대입니다.
    보드(초록색 기판) 한 장에 컴퓨터에 필요한 게 다 붙어 있어요: 두뇌 칩(CPU 포함), 메모리(RAM), USB 포트, 랜선 포트, HDMI(화면 연결), 카메라 연결부, 전원부. 이렇게 기판 한 장으로 된 컴퓨터를 SBC(Single Board Computer, 싱글보드 컴퓨터)라고 부릅니다.
    데스크탑과 비교: 데스크탑은 본체 안에 메인보드·CPU·그래픽카드·저장장치가 각각 따로 꽂혀 있고 크고 전기를 많이 씁니다. 라즈베리파이는 이걸 신용카드 크기 기판 하나에 몰아넣어 싸고(수만~십만 원대), 작고, 전기를 적게 씁니다. 대신 성능은 낮아요.
    하드디스크는? 따로 없고 SD카드(카메라 메모리카드 같은 것)를 꽂아서 거기에 운영체제와 파일을 저장합니다. → B장 "굽기"와 연결됩니다.
    왜 AI 실습에 쓰나? 리눅스가 돌아가는 진짜 컴퓨터라서 파이썬, OpenCV(영상 처리), AI 실행 라이브러리를 그대로 설치할 수 있습니다. 동시에 작고 저렴해서 "로봇·CCTV·자동차 안의 작은 컴퓨터에서 AI 돌리기"를 연습하기 좋아요.
    라즈베리파이 5의 두뇌 칩: Broadcom BCM2712. 안에 CPU(Arm Cortex-A76 4코어)와 GPU가 들어 있고, NPU는 없습니다. 그래서 이 실습의 AI 추론은 CPU가 계산합니다.
    SoC, CPU, GPU, NPU는 각각 뭐가 달라?
    이름뭔가비유
    CPU무엇이든 계산하는 범용 두뇌. 순서대로 복잡한 일을 잘함뭐든 하는 만능 직원 몇 명
    GPU원래 그래픽용. 단순 계산 수천 개를 동시에 처리 → 딥러닝 학습에 많이 씀단순 작업을 동시에 하는 직원 수천 명
    NPU딥러닝 계산(행렬 곱셈 등)만을 위해 만든 전용 칩. 추론이 빠르고 전기를 적게 씀AI 계산만 하는 전문 기술자
    SoCSystem on Chip. CPU·GPU·(NPU)·영상처리 등을 칩 하나에 합친 것. 스마트폰·라즈베리파이·TOPST가 다 SoC를 씀한 건물에 여러 부서가 입주한 것
    YOLO 같은 모델을 어디서 돌리나? YOLOv11n처럼 작은 모델은 CPU로도 돌아가지만 느립니다(초당 몇 장 수준). NPU가 있으면 훨씬 빠르지만, 보통 모델을 그 NPU 전용 형식으로 변환하는 과정이 추가로 필요해요.
    텔레칩스 칩은 CPU야 NPU야? TOPST 보드들은 뭐가 달라?
    텔레칩스(Telechips)는 회사 이름입니다(한국의 자동차용 반도체 회사). 이 회사가 만든 칩은 라즈베리파이 칩처럼 SoC이고, 제품에 따라 NPU가 들어 있기도 하고 없기도 해요. TOPST는 텔레칩스 칩을 올린 교육·개발용 보드 브랜드입니다.
    장비칩CPUNPU
    라즈베리파이 5Broadcom BCM2712Cortex-A76 4코어없음
    TOPST D3-G텔레칩스 Dolphin3 (TCC8050)A72 4 + A53 4 + R5 1없음 (GPU만)
    TOPST AI-G텔레칩스 N-DolphinA53 4코어있음, 8 TOPS
    APACHE5넥스트칩 NVS2900A53 4코어있음, 1.6 TOPS (자동차 ADAS용)
    TOPS = NPU가 1초에 할 수 있는 연산 횟수(조 단위). 클수록 AI 계산이 빠릅니다.
    출처: TOPST AI-G 공식 · TOPST D3-G 공식 · Nextchip APACHE5 (2026-09 확인)
    "윌텍 실습보드"는 그냥 라즈베리파이랑 뭐가 달라?
    교육업체 윌텍(Willtek)이 라즈베리파이 5에 실습용 부품을 붙여 만든 보드입니다. 안내서 2~3쪽 기준으로 붙어 있는 것들은 다음과 같아요.
    • LCD 화면(터치 가능): 보드 결과를 바로 볼 수 있음
    • ON/OFF 스위치, 전원 LED
    • USB 포트 4개: 여기에 USB 웹캠을 꽂음
    • 이더넷(랜선) 포트, HDMI 2개
    ⚠️ 전원 끄기 주의(안내서 17쪽): 전원선을 그냥 뽑으면 SD카드 파일이 깨질 수 있습니다. LCD의 Shutdown 버튼, 터미널의 sudo shutdown 명령, 또는 ON/OFF 스위치를 짧게 두 번 누르는 방법으로 끄세요. 3~5초 길게 누르면 강제 종료라 비상시에만 씁니다.

    B. OS 이미지와 "굽기"

    "이미지"가 뭐야? 사진 말하는 거야?
    사진이 아닙니다. 여기서 이미지(image)는 저장장치 하나를 통째로 복사해 둔 파일이에요.
    RPI5_Image_32GB_260316a.img(약 32GB)는 "설정이 다 끝난 라즈베리파이용 32GB SD카드"를 그대로 떠 놓은 복제본입니다. 안에는 다음이 이미 들어 있습니다.
    • 운영체제(OS): 라즈베리파이용 리눅스
    • 사용자 계정 willtek
    • 파이썬 가상환경과 필요한 라이브러리(OpenCV, tflite_runtime 등)
    • 네트워크 설정(보드 IP 192.168.10.3)
    OS(운영체제) = 컴퓨터를 켜면 제일 먼저 돌아가는 밑바닥 프로그램(윈도우, 리눅스 등). 다른 프로그램들은 전부 OS 위에서 돌아갑니다.
    비유: 강사가 완벽하게 세팅한 컴퓨터를 통째로 사진 찍듯 복제해 둔 것. 수강생은 하나하나 설치할 필요 없이 복제본을 SD카드에 붓기만 하면 똑같은 환경이 됩니다.
    파일 이름 뜻: RPI5=라즈베리파이5 · 32GB=SD카드 용량 · 260316=2026-03-16 제작 · a=그날 버전.
    "굽는다"는 게 무슨 뜻이야?
    이미지 파일을 SD카드(또는 USB·CD)에 그대로 써 넣는 것을 흔히 "굽는다"고 합니다. 옛날 CD 굽기(레이저로 CD에 기록)에서 온 말이에요.
    그냥 복사 붙여넣기와 다른 점: 파일 하나를 SD카드에 복사하면 SD카드 안에 .img 파일 하나만 생깁니다. 굽기는 그 파일 내용을 풀어서 SD카드의 처음부터 끝까지 똑같이 재현해요. 부팅에 필요한 영역까지 복원돼서, 라즈베리파이에 꽂으면 바로 켜집니다.
    순서:
    1. PC에 SD카드 리더기로 32GB 이상 microSD카드를 꽂음
    2. win32diskimager-1.0.0-install.exe 설치 후 실행 (이미지를 굽는 프로그램)
    3. Image File에 .img 선택 → Device에 SD카드 드라이브 선택 → Write
    4. 끝나면 SD카드를 라즈베리파이에 꽂고 전원 켜기
    ⚠️ Device(드라이브 문자)를 잘못 고르면 그 드라이브 내용이 전부 지워집니다. SD카드 드라이브가 맞는지 꼭 확인하세요. 교육장에서 이미 구워진 보드를 주는 경우라면 이 과정은 안 해도 됩니다.

    C. PC와 보드 연결하기

    PC에서 보드를 어떻게 조종해? (보드 설치 안내서 요약)
    보드에 키보드·마우스를 직접 꽂는 대신, 랜선으로 PC와 연결해서 PC에서 원격 조종합니다.
    단계하는 일안내서
    1. 선 연결HDMI, 전원, 랜선(PC에 랜 포트가 없으면 USB-이더넷 동글 사용), USB 웹캠3쪽
    2. 주소 맞추기보드 IP 192.168.10.3(이미 설정됨), PC IP를 192.168.10.2로 설정5~9쪽
    3. 연결 확인PC 명령창에서 ping 192.168.10.38쪽
    4. 원격 접속MobaXterm으로 SSH 접속 · 아이디 willtek / 암호 123412~14쪽
    5. 파일 보내기MobaXterm 왼쪽 탐색기에 파일을 끌어다 놓기15쪽
    6. 실행가상환경 켜기(프롬프트에 (env) 표시) → python 파일명.py16쪽
    결과를 보드 LCD에 띄우려면 실행 전에 터미널에 export DISPLAY=:0.0 입력(16쪽).
    IP 주소가 뭐고 왜 PC랑 보드를 192.168.10.2 / .3으로 맞춰?
    IP 주소 = 네트워크 안에서 기기를 찾아가는 집 주소입니다. 데이터를 보내려면 받는 쪽 주소를 알아야 해요.
    192.168.10.2(PC)와 192.168.10.3(보드)는 앞 세 칸이 같습니다. 같은 동네(같은 네트워크)라는 뜻이라 랜선 하나로 서로 바로 찾아갈 수 있어요. 끝자리만 달라서 서로 구분됩니다. 설정 화면의 255.255.255.0(서브넷 마스크)은 "앞 세 칸이 같으면 같은 동네"라는 규칙을 적은 값이에요.
    ping = "거기 있어?" 하고 신호를 보내 답이 오는지 확인하는 명령. 답이 오면 선과 주소 설정이 맞은 거예요.
    SSH랑 MobaXterm은 뭐야?
    SSH(Secure Shell) = 네트워크로 다른 컴퓨터에 암호화된 연결로 원격 로그인해서, 그 컴퓨터의 명령창에 명령을 입력할 수 있게 해 주는 통신 규칙입니다. 기본 포트 번호는 22예요.
    MobaXterm = 윈도우에서 SSH 접속을 편하게 해 주는 프로그램입니다. 명령창과 파일 탐색기(끌어다 놓기로 파일 전송)가 한 화면에 있어요. 폴더에 있는 건 Portable 버전이라 설치 없이 압축만 풀고 실행하면 됩니다.
    비유: SSH = 보드라는 집의 원격 출입 열쇠. MobaXterm = 그 열쇠를 쓰기 편하게 만든 리모컨.
    /home/willtek/work/는 뭐야?
    보드(리눅스) 안의 폴더 경로입니다. 윈도우의 C:\Users\LG\와 같은 개념이에요.
    • 리눅스는 드라이브 문자(C:) 없이 /(루트)에서 시작하고, 구분자로 \ 대신 /를 씁니다.
    • /home/willtek/ = 사용자 willtek의 개인 폴더 (윈도우의 C:\Users\LG\에 해당)
    • /home/willtek/work/ = 그 안의 work 폴더. readme 지시대로 보드 예제(examples 폴더)를 여기에 복사합니다.

    E. 딥러닝 모델

    YOLOv11n이 뭐야? 이름의 n은?
    YOLO(You Only Look Once) = 사진을 한 번만 보고 "어디에(박스) 무엇이(클래스) 있는지"를 동시에 찾는 객체 탐지(Object Detection) AI 모델입니다. Ultralytics라는 회사가 v11 버전을 만들었어요.
    n = nano(가장 작은 크기). n < s < m < l < x 순으로 커지고, 클수록 정확하지만 느립니다. 라즈베리파이 CPU에서 돌려야 하니 제일 작은 n을 씁니다.
    분류 vs 탐지: 앞 단계의 MobileNetV2 실습은 분류(사진 한 장 전체가 가위냐 바위냐 보냐)였고, YOLO는 탐지(화면 속 손이 어디 있고, 각각 무엇인지)입니다. 탐지는 손이 여러 개여도 되기 때문에 두 사람의 승패 판정으로 확장할 수 있어요.
    "Pretrained / 파인튜닝(Fine-tuning)"은 무슨 뜻이야?
    Pretrained(사전학습) = 누군가 이미 엄청난 양의 사진(사람·자동차·개 등 80종)으로 학습시켜 둔 모델. yolo11n.pt가 이것입니다.
    파인튜닝 = 이 모델을 출발점으로 우리 데이터(가위바위보 사진)로 추가 학습시켜 우리 목적에 맞게 고치는 것.
    비유: 운전면허 있는 사람에게 트럭 운전만 추가로 가르치기. 처음부터 운전을 가르치는 것보다 훨씬 빠르고, 적은 데이터로도 잘 됩니다.
    노트북의 학습 명령 설정: 입력 크기 320×320, 전체 데이터를 80번 반복(epochs=80), 한 번에 32장씩(batch=32), 사진을 회전·뒤집기(degrees, flipud, fliplr, mosaic)해서 데이터를 불리는 증강(augmentation) 사용.
    변환(export)과 양자화는 왜 해? best_int8, w8a32는 뭐가 달라?
    변환: 학습용 .pt는 PyTorch가 있어야 돌아갑니다. 라즈베리파이에서는 가벼운 tflite 실행기를 쓰기 때문에 .tflite로 바꿔요.
    양자화(Quantization): 모델 안의 숫자(가중치)를 더 적은 비트로 저장해서 파일을 줄이고 계산을 빠르게 하는 것. 소수점 숫자(32비트)를 정수(8비트)로 반올림하는 셈이라 정확도는 조금 떨어질 수 있습니다.

    EX_06의 train_gen = img_gen_train.flow(train_data, train_labels, seed=1)이 뭘 하는 거야? "제너레이터"가 뭐야?
    한 줄로: 사진 2,172장과 정답을 "변형 기계"에 걸어 두고, 학습이 "다음 32장 주세요"라고 할 때마다 즉석에서 변형한 32장을 내주는 통로를 만드는 것이에요.
    단계무슨 일비유
    ① img_gen_train = ImageDataGenerator(뒤집기, 이동, 밝기, 줌…)"어떻게 변형할지" 설정만 해 둔 기계. 아직 사진은 없음레시피만 적힌 빈 기계
    ② train_gen = img_gen_train.flow(train_data, train_labels, seed=1)기계에 사진 배열과 정답 배열을 연결. 아직 아무것도 변형하지 않음. train_gen은 "꺼내기 버튼"이 달린 통로재료 창고를 기계에 연결
    ③ model.fit(train_gen, …)fit이 학습 도중 통로에 "다음!" 하고 요청하면 그때 32장을 무작위로 뽑아 각각 다르게 변형해서 넘겨줌. 정답 32개도 같이 넘겨줌버튼 누를 때마다 32인분 나옴
    ④ 68번 반복 = 1 epoch2,172 ÷ 32 ≈ 68번 꺼내면 모든 사진을 한 번씩 본 것. 다음 epoch에는 같은 사진이 다르게 변형돼 나옴같은 재료, 매번 다른 요리
    왜 "미리 다 만들어 두지" 않고 이렇게 하나? 2,172장을 30가지로 미리 변형해 저장하면 6만 장, 수 GB가 된다. 제너레이터는 필요한 순간에 32장만 만들고 버리기 때문에 메모리를 거의 안 쓴다. 대신 매번 만드느라 시간이 든다(epoch당 3초 → 28초).
    정답은 어떻게 되나? 사진만 변형되고 정답은 그대로 따라간다. 뒤집힌 가위도 가위, 어두운 바위도 바위. flow()에 train_labels를 같이 넣은 이유가 이것. 그래서 fit에 정답 인자가 따로 없다.
    seed=1은? "무작위"의 시작점을 고정하는 것. 컴퓨터의 무작위는 시작 숫자(seed)가 같으면 같은 순서로 나온다. 1로 고정해 두면 다시 실행해도 같은 순서로 같은 변형이 나와서 결과를 재현할 수 있다. 다른 숫자로 바꾸면 변형 순서가 달라진다(학습 결과는 비슷).

    ReLU가 "없으면 층을 아무리 쌓아도 직선 하나와 같아진다"는 게 뭔 말이야? 왜 직선 하나면 안 되는데?
    층 하나가 하는 계산이 사실 일차함수(y = ax + b)라서, 그냥 이어 붙이면 아무리 많아도 일차함수 하나로 합쳐져 버린다는 뜻이다. 숫자로 보면 바로 보인다. 
    층1:  y = 2x + 1
층2:  z = 3y + 4
    x=5를 넣으면 y = 2(5)+1 = 11, z = 3(11)+4 = 37. 그런데 두 식을 합치면 z = 3(2x+1)+4 = 6x+7이고, 여기에 x=5를 넣어도 37이다. 층 2개가 층 1개(6x+7)와 완전히 같다. 100개를 쌓아도 마찬가지라 계산량만 100배 들고 표현력은 그대로다. 깊게 쌓는 의미가 사라지므로 "딥"러닝이 성립하지 않는다.

    가위바위보도 같다. "픽셀값이 클수록 가위"같은 단순 비례 관계가 아니다. 손가락 두 개가 V자로 벌어져 있으면 가위인데, 이건 픽셀값의 곱셈·덧셈을 일렬로 아무리 늘어놔도 표현되지 않는다. 꺾임이 있어야 "여기는 밝고 저기는 어두우면"같은 조건 판단이 생긴다.

    FPGA가 뭐야? CPU·NPU랑 뭐가 달라?
    FPGA(Field Programmable Gate Array) = 내부 회로를 사용자가 다시 짤 수 있는 칩입니다.
    • CPU는 회로가 공장에서 고정돼 있고, 프로그램(명령어 순서)을 바꿔서 다른 일을 시킵니다.
    • FPGA는 회로 자체를 Verilog 같은 하드웨어 설계 언어로 설계해서 칩에 심습니다. 그래서 특정 계산 전용 회로를 만들면 CPU보다 훨씬 빠르게 처리할 수 있어요.
    • NPU·GPU는 특정 계산에 맞춰 공장에서 고정된 전용 칩이고, FPGA는 전용 칩을 실험해 볼 수 있는 레고판에 가깝습니다. 반도체 회사들이 칩을 실제로 만들기 전에 FPGA로 먼저 검증하기도 해요.
    비유: CPU = 만능 요리사에게 레시피를 바꿔 주기. FPGA = 부엌 구조 자체를 그 요리 전용으로 뜯어고치기.
    교육과의 연결: 과정 장비인 Basys3에도 같은 Artix-7 계열 칩(XC7A35T)이 들어 있어요. 개발 도구도 같은 Vivado입니다. 즉 지인 키트의 FPGA 카드는 교육에서 배우는 FPGA와 같은 계열이에요.
    M.2, PCIe는 뭐고, 라즈베리파이에 FPGA를 왜 붙여?
    PCIe = 컴퓨터 본체와 확장 장치(그래픽카드, SSD 등)가 초고속으로 데이터를 주고받는 통로 규격입니다. "레인(lane)" 수가 많을수록 차선이 넓은 도로라 빠릅니다.
    M.2 = 그 PCIe 신호를 쓰는 작은 막대형 카드 규격(노트북 SSD 모양). 이 FPGA 카드는 SSD처럼 생긴 M.2 M-Key 카드라서 SSD 자리에 꽂힙니다.
    라즈베리파이 5는 기판에 PCIe 단자가 1레인 있어서, 확장 보드와 FPC 케이블로 M.2 장치를 붙일 수 있습니다. 보통은 SSD를 꽂지만, 이 키트는 그 자리에 FPGA를 꽂은 거예요.
    왜? "CPU(라즈베리파이) + 가속기(FPGA)" 구조를 작게 연습할 수 있기 때문입니다. 라즈베리파이가 데이터를 PCIe로 FPGA에 보내고, FPGA의 전용 회로가 계산해서 결과를 돌려주는 방식이에요. 데이터센터의 "서버 + 가속기 카드"를 손바닥 크기로 줄인 셈입니다. 카드 판매 사진 기준으로 FPGA 쪽 고속 통로(GT 송수신기)는 4개(6.6Gbps)입니다. 하지만 라즈베리파이 5 쪽 PCIe가 1레인이라, 이 조합에서는 1레인만 쓰게 됩니다.

    • ASYM(비대칭): 최솟값 ~ 최댓값을 그대로 256칸에. 치우친 분포에 효율적이지만 기준점(zero point) 계산이 추가됩니다.

    ① 전처리 재설계: 작은 모델(v8n/m)용 코드는 사진을 float32로 바꾸고 255로 나눴어요(이번 EX_03과 같은 방식). 그런데 대형 모델 ENF는 입력을 UINT8(0~255 정수) 그대로 받도록 컴파일돼서, 기존 코드로는 입력 타입 불일치 오류가 났습니다. 그래서 float 변환과 정규화를 빼고 정수 그대로, 메모리가 연속되게 넣도록 바꿨어요. (정규화는 NPU 안에서 처리)
    ② 후처리 재설계 (DFL): YOLO의 마지막 부분(Detection Head)은 박스 좌표를 바로 내지 않아요. "경계가 이 칸일 확률 분포"(DFL, Distribution Focal Loss 방식)를 3가지 크기의 격자(multi-scale)마다 냅니다. 그런데 이 Head 부분(Reshape·Sigmoid·Concat)을 NPU에서 INT8로 돌리면 정확도가 크게 떨어졌어요. 그래서 NPU는 Head 직전(Backbone·Neck)까지만 계산하고, 나머지는 CPU 파이썬 코드로 옮겼습니다. 옮긴 계산은 다음과 같아요.
    1. 격자 크기별 기준점(Anchor Grid) 만들기
    2. 확률 분포 → 실제 거리 → 박스 좌표 변환(dist2bbox)
    3. 3개 스케일 결과 합치기
    4. 클래스 점수 결합 + NMS
    이번 EX_03과 비교: 교육 모델은 변환할 때 1~3번까지 모델 안에 포함돼서, 출력이 이미 [cx, cy, w, h, 가위, 바위, 보] × 2100개로 정리돼 나와요. 그래서 코드에는 4번(점수 필터 + NMS)만 있습니다. 즉 EX_03의 후처리 = 대학원 때 직접 구현한 후처리의 마지막 단계예요. 왜 교육 코드는 Head까지 모델에 넣어도 되나? 라즈베리파이 CPU 기본 실행(best.tflite)은 FP32라서 Head 정확도 문제가 없어요. INT8판(best_int8)도 입출력은 float32로 둔 채 내부만 양자화했습니다(노트북 셀 주석 "입력과 출력은 float32"). 다만 INT8판에서 Head 쪽 정확도가 얼마나 떨어지는지는 교육장에서 비교해 볼 거리예요.
    보고서의 Worker, Batch, In-Flight, 멀티프로세스, Queue는 뭐였어?
    배경은 이거예요. NPU가 아무리 빨라도, 사진 준비(CPU)와 화면 출력이 느리면 NPU가 놀면서 기다립니다. 이 "노는 시간"을 없애는 게 파이프라인 최적화였어요.

    USB 웹캠이 영상을 보드로 보낼 때의 포장 방식을 MJPG로 바꾸는 줄이다. FOURCC는 Four Character Code, 영상 형식을 네 글자로 적는 오래된 관례다(MJPG, YUYV, H264). cv2.VideoWriter_fourcc('M','J','P','G')는 그 네 글자를 OpenCV가 쓰는 정수 하나로 바꿔 준다.
    USB 웹캠의 기본값은 대개 YUYV(무압축)로, 픽셀당 2바이트를 그대로 보낸다. 640×480이면 한 장에 640×480×2 = 614,400바이트(약 600KB), 30장/초면 초당 약 18MB ≒ 147Mbps다. USB 2.0의 실효 대역폭(약 300Mbps)이 금방 찬다. 1280×720이면 한 장이 1.8MB라 30fps에 442Mbps가 되어 한계를 넘고, 그러면 카메라가 알아서 fps를 5~10으로 떨어뜨린다. MJPG는 한 장씩 JPEG로 압축해 보내 데이터가 1/10 안팎으로 줄기 때문에 같은 USB 선으로 더 높은 해상도·fps가 나온다. 대신 보드가 매 프레임 JPEG를 푸는 CPU 작업을 한다.

    같은 계산인데 왜 빨라지나

    이유설명
    ① 메모리 이동이 줄어든다CPU가 가중치를 RAM에서 꺼내 오는 시간이 계산 시간보다 오래 걸리는 경우가 많다. 9.5MB를 옮기던 것이 2.9MB가 되니 그만큼 빨라진다. 캐시(빠른 임시 저장소)에 더 많이 들어가는 효과도 크다
    ② 한 번에 더 많이 처리한다ARM CPU의 SIMD 레지스터는 128비트다. float32는 한 번에 4개, int8은 16개가 들어간다. 명령 하나로 처리하는 개수가 최대 4배
    ③ 정수 연산이 더 단순하다float32는 지수·가수를 따로 다뤄야 하고, 정수는 그냥 더하고 곱하면 된다
    그럼 왜 4배가 아니라 2.15배야?
    int8로 곱한 결과를 그대로 int8에 담으면 넘치므로 int32로 누산하고 다시 int8로 환산하는 과정이 붙는다. 또 int8로 안 바뀌고 남는 부분(편향은 int32)이 있고, 메모리 대역폭에도 한계가 있다. 그래서 크기 배수(3.31배) > 속도 배수(2.15배)가 되는 것이 정상이다. 속도를 크기만큼 끌어올리려면 int8 전용 연산기(NPU)가 필요하다.

    ② 숫자 형식계산 하나의 비용float32 → int8 양자화이번 실습 (2.15배) + 산학 프로젝트 INT8 PTQ
    ③ 하드웨어계산기 자체의 성능CPU → GPU → NPU산학 프로젝트 (WARBOY NPU)
    짐을 옮기는 일에 비유하면, ①은 짐 자체를 줄이는 것, ②는 짐을 압축해 한 번에 더 들고 가는 것, ③은 더 힘센 사람을 부르는 것이다. 셋은 곱해서 작용하므로 함께 쓸 수 있다. 산학 프로젝트에서 NPU(③)를 쓰면서도 INT8 PTQ(②)를 했던 이유가 이것이고, 많은 NPU는 애초에 int8만 처리하므로 ②가 ③을 쓰기 위한 전제 조건이기도 하다.
    예전 생각을 고쳐 말하면: "하드웨어가 좋아야 빠르다"는 절반만 맞다. 같은 하드웨어에서도 모델을 어떻게 준비하느냐로 2배 이상 갈리고, 반대로 좋은 하드웨어를 사도 모델이 그 하드웨어에 맞는 형식이 아니면 성능이 안 나온다. (Lightweighting 학습노트 12·18·21절)

    L. 하드웨어(Verilog) 양자화 코드 읽기

    이 Verilog 양자화 코드는 uniform 양자화야, non-uniform 양자화야?
    // Quantization (saturate to 8-bit, with rounding)
assign w_quan_out_0 = (|w_relu_out_0[31:15]) ? 8'd255
                      : ((&w_relu_out_0[14:7]) ? w_relu_out_0[14:7]
                      :  (w_relu_out_0[14:7] + w_relu_out_0[6]));
    Uniform(균일) 양자화다. 판단 기준은 하나다. 출력 한 칸(1 LSB)이 입력의 같은 폭을 대표하느냐. 이 코드는 32비트 값을 [14:7]로 잘라 쓰는데, 비트 7~14를 꺼내는 것은 128로 나누기와 같다. 출력 0은 입력 0~127, 출력 1은 128~255, 출력 2는 256~383… 모든 칸의 폭이 128로 똑같다. 즉 scale = 128, zero point = 0인 선형 양자화이고, tflite의 실수 = (정수 − zero) × scale과 같은 식에서 scale이 2의 거듭제곱이라 곱셈 대신 비트 자르기(시프트)로 구현한 것이다.
    코드 조각뜻
    w_relu_out_0[31:15]입력은 ReLU를 거친 32비트 값(음수 없음). 비트 15 이상이 하나라도 1이면 값이 32,768 이상 = 255×128을 넘는다는 뜻.
    (|w[31:15]) ? 8'd255|는 reduction OR("하나라도 1이냐"). 넘치면 255로 포화(saturate). 그릇보다 큰 값은 잘라 최댓값으로.
    w[14:7]8비트를 꺼낸다 = 입력 ÷ 128의 몫. 이것이 양자화의 본체(scale 128).
    w[6]버려지는 비트 중 가장 위 = ÷128의 나머지가 64 이상인지. 이걸 더하면 반올림(0.5 이상 올림)이 된다. 안 더하면 내림(버림).
    (&w[14:7]) ? w[14:7]&는 reduction AND("전부 1이냐"). 몫이 255(=11111111)일 때 반올림으로 1을 더하면 256이 되어 8비트를 넘쳐 0이 된다. 그 경우만 더하지 않고 255 그대로. 반올림 오버플로 방지.
    : (w[14:7] + w[6])그 외에는 몫 + 반올림 비트.
    입력 (ReLU 출력)÷128 몫 [14:7][6]출력
    0 ~ 63000
    64 ~ 1910 또는 11 또는 01
    32,704 ~ 32,7672551255 (더하지 않음)
    32,768 이상——255 (포화)
    Non-uniform이었다면 칸 폭이 값에 따라 달라진다. 예: 로그 양자화(작은 값은 촘촘히, 큰 값은 성기게, 2의 거듭제곱 간격), 또는 Clustering처럼 k-means로 정한 대푯값 8~16개(간격 제각각). 그런 코드는 비트 자르기 한 번으로는 안 되고 비교기 사다리나 조회표(LUT)가 필요하다. 이 코드는 시프트 + 반올림 + 포화 세 동작뿐이므로 uniform이다.
    Colab에서 본 tflite INT8은 scale이 0.0039 같은 임의의 실수였다. 하드웨어에서는 곱셈기가 비싸서 scale을 2의 거듭제곱(여기선 128)으로 골라 비트 자르기로 대신한다. 같은 uniform 양자화인데 구현이 소프트웨어(곱셈)와 하드웨어(시프트)로 다를 뿐이다. 부호 없는 0~255(uint8)인 이유는 ReLU 뒤라 음수가 없어서다.

    비유: 한 사람이 쓴 손글씨 33장만 보고 글씨를 배운 뒤, 다른 사람 글씨를 읽으라는 것과 같다. 그 사람 글씨는 완벽하게 읽는다.

    흰 배경에서는 잘 되는데 밤색 티 앞에서 하면 인식이 안 돼. 왜?
    학습 사진 104장의 배경이 전부 "밝은 무채색 벽" 한 종류이기 때문이다. 추측이 아니라 104장의 픽셀을 직접 재서 나온 값이다.
    측정 항목값뜻
    배경 밝기 V (0~255)최소 131, 평균 153, 최대 176밝은 쪽에만 몰려 있다
    V가 120보다 어두운 사진0장 / 104장어두운 배경을 한 번도 본 적 없다
    배경 평균색 BGRB 140 / G 144 / R 146세 값이 비슷 = 거의 무채색(회색 벽)
    손(박스 안) 평균색 BGRB 131 / G 139 / R 160R이 21 높다 = 살색(붉은기)

    모델이 실제로 배운 규칙

    "밝고(V 131~176) 색이 없는 벽 앞에 있는, 붉은기 도는 덩어리 = 손"

    밤색 티가 그 규칙을 어떻게 깨나

    밤색(짙은 갈색)은 ① 어둡다 → 학습에서 본 적 없는 밝기다(V가 최소치 131보다 아래). 그리고 ② 붉다 → 모델이 "손"의 표시로 쓰던 붉은기가 배경에도 깔린다. 의지하던 단서 두 개가 동시에 무너지니 못 찾는다. 흰 벽은 정확히 학습 분포 안이라 잘 되는 것이다.
    비유: "흰 종이 위의 검은 글씨"만 보고 글을 배운 사람에게 검은 종이 위의 짙은 회색 글씨를 내미는 것과 같다. 글자 모양은 그대로인데 못 읽는다.
    직접 재 보는 법: 05_Object_Detection_Based_On-Device_AI/bg_check.py를 보드에서 돌리면 지금 카메라에 보이는 배경의 V와 R−B를 1초마다 찍어 학습 범위와 비교해 준다. 밤색 티를 비추고 한 번, 흰 벽을 비추고 한 번 재면 "왜 안 되는지"가 숫자로 나온다.

    고치는 순서

    방법드는 시간효과
    밝은 무채색 벽 앞에서 시연0분시연은 되지만 원인은 그대로
    조명 켜서 배경을 밝게0분V를 학습 범위로 끌어올린다
    그 배경에서 사진 찍어 데이터 추가 후 재학습30분근본 해결
    재학습 시 색·밝기 증강 강화 (hsv_v=0.6 hsv_s=0.9)0분보조 수단. 없는 배경을 만들어 주지는 못한다
    근데 학습 결과는 mAP50이 0.995였잖아. 거의 만점인데 왜 실제로는 못 맞춰?
    시험지와 문제집이 같은 책이었기 때문이다. test 22장도 train 82장과 같은 자리·같은 조명에서 찍혔다. 측정해 보면 test의 배경 밝기 V 평균도 160이고, 역시 V가 120 아래인 사진이 0장이다.
    그래서 mAP50 0.995는 거짓말은 아니지만, 이런 뜻일 뿐이다.
    "이 모델은 밝은 회색 벽 앞에서 찍은 손이라면 거의 다 맞춘다."
    "밤색 티 앞에서도 맞춘다"는 한 번도 시험한 적이 없다.
    이것을 분포 차이(domain gap)라고 한다. 학습·검증 데이터가 놓인 조건과 실제 쓰는 조건이 다른 것이다.
    여기서 배울 것 — 포트폴리오·면접에서 그대로 쓸 수 있다.
    검증 점수가 높다는 것은 "실전에서 잘 된다"가 아니라 "검증 데이터와 닮은 상황에서 잘 된다"는 뜻이다. 점수를 믿으려면 검증 데이터가 실제 쓸 환경을 담고 있어야 한다. 이 데이터셋은 안 담고 있었고, 그걸 밤색 티 앞에서 직접 확인한 것이다.
    숫자 하나로 정리: mAP50 0.995 vs 밤색 티 앞 실패. 이 간극 자체가 이번 프로젝트의 가장 좋은 이야깃거리다.
    얼굴도 가위바위보로 인식해서 손 2개 + 얼굴 1개 = 3개가 돼. 어쩔 수 없는 거야?
    어쩔 수 없는 게 아니라, 같은 원인의 다른 증상이다. 고칠 수 있다. 학습 로그의 82 images, 0 backgrounds, 0 corrupt가 근거다. YOLO에서 background는 "라벨 파일이 없는(= 찾을 것이 아무것도 없는) 사진"을 뜻하고, 모델은 그런 사진으로 "여기엔 아무것도 없다"를 배운다. 이 데이터셋에는 그런 사진이 0장이라, 모델은 "아무것도 없음"이라는 답을 배운 적이 없다. 게다가 얼굴은 살색이고 타원형이라 손과 특징이 겹친다.
    고치는 법 — 배경 사진 추가가 정석이다.
    EX_01_Image_Capture.py로 얼굴만 나오고 손은 없는 사진을 8~10장 찍고, 라벨 파일을 만들지 않은 채 학습 폴더에 넣는다. Ultralytics가 자동으로 background로 인식한다. 권장 비율은 전체의 약 10%다. 82장 기준 8~10장. TS-10(밤색 티)과 같은 촬영 한 번으로 둘 다 해결된다 — 어두운 배경 + 얼굴을 함께 찍으면 된다.

    코드

    cap = cv2.VideoCapture(0)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*'MJPG'))   # ← 이것
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 320)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 240)
cap.set(cv2.CAP_PROP_FPS, 30)
    순서가 중요하다. 형식(FOURCC)은 해상도보다 먼저 지정해야 드라이버가 제대로 받아들인다. 그리고 set()은 명령이 아니라 부탁이다. 카메라가 지원하지 않으면 조용히 무시된다. 그래서 설정 직후 cap.get()으로 실제로 바뀌었는지 확인해서 출력하도록 코드를 넣어 두었다.
    왜 지금 이게 필요한가 — 04 실습 최적화에서 파이프라인을 한 프레임 60.5 → 23.2 ms까지 줄였는데, 카메라가 초당 18.5장밖에 주지 않아 처리한 프레임의 57.1%가 같은 그림(중복)이었다. MJPG로 바꾸면 그 상한 자체가 올라갈 수 있다. 지금까지의 최적화가 실제 성능으로 바뀌는지가 여기에 달려 있다. camera_check.py로 다섯 가지 조건(현재 / MJPG / FPS 30 요청 / MJPG+30 / 자동노출 끔)을 5초씩 재서 비교할 수 있다.
    FOURCC는 형식을 나타내는 네 글자 코드(Four Character Code)라는 뜻이다. 'MJPG', 'YUYV', 'H264' 같은 것들이다. 강사님이 "엠펙"이라고 하신 것은 이 MJPG를 가리킨 것으로 보인다(MPEG은 다른 동영상 압축 규격이다).
    강사님이 tflite_runtime을 ai_edge_litert로 바꾸라는데, 뭐가 다른 거야?
    다른 물건이 아니라 같은 물건의 새 이름이다. 구글이 TensorFlow Lite를 LiteRT(Lite Runtime)로 이름을 바꾸면서 파이썬 패키지 이름도 옮겨 갔다.
    시기패키지쓰는 법
    옛 이름tflite_runtime.interpreterimport tflite_runtime.interpreter as tflite
    새 이름ai_edge_litert.interpreterimport ai_edge_litert.interpreter as tflite
    아래 코드는 한 줄도 안 고쳐도 된다. as tflite로 별명을 똑같이 붙였기 때문이다. tflite.Interpreter(model_path=...), tflite.Interpreter(...).invoke() 전부 그대로 돌아간다. 이것이 as(별명)를 쓰는 이유다 — 패키지 이름이 바뀌어도 코드 본문을 지킬 수 있다.

    왜 섞는 쪽이 유리한가

    모델은 "라벨과 끝까지 같이 가는 것"을 배운다. 여러 장에서 공통으로 나타나는 것만 남기고 나머지는 버린다.
    배경이 한 종류배경이 여러 종류
    사진마다 공통인 것손 모양 + 밝은 회색 벽손 모양뿐
    모델이 배우는 것둘 다 쓴다. 벽이 더 쉬우니 벽에 기댄다기댈 게 손밖에 없다 → 손을 제대로 배운다
    결과벽이 바뀌면 무너진다배경이 바뀌어도 버틴다
    핵심: 배경이 하나뿐이면 "밝은 회색 벽"이 "손이 있다"를 100% 예측해 버린다. 모델 입장에서는 손가락 모양을 힘들게 배우는 것보다 벽을 보는 게 훨씬 쉽다. 이렇게 쉬운 지름길을 배워 버리는 것을 지름길 학습(shortcut learning)이라고 한다. 지금 밤색 티 앞에서 실패하는 게 바로 그 증거다 — 혼동은 섞어서 생기는 게 아니라, 안 섞어서 이미 생겼다.

    강사님 학습 명령이 이미 배경을 흩뜨리고 있다

    !yolo detect train model=yolo11n.pt data={DATA} \
  imgsz=320 epochs=80 batch=32 device=0 workers=4 \
  project={project_root} degrees=15.0 flipud=0.5 \
  fliplr=0.5 mosaic=1.0 name=rps_yolo11n
    mosaic=1.0은 사진 4장을 한 장으로 이어 붙여 학습시키는 증강이다. 손 주변에 엉뚱한 사진 조각이 오도록 일부러 만드는 것이고, 목적이 정확히 "배경에 기대지 마라"다.
    즉 배경을 섞는 것은 이미 강사님 설정이 하고 있는 일이다. 다만 증강은 데이터에 있는 것만 섞을 수 있다. 어두운 배경이 한 장도 없으면 만들어 낼 수 없다. 그래서 찍어서 넣어 줘야 하는 것이다.

    진짜 조심해야 할 것 — 배경과 클래스를 짝지으면 안 된다

    밤색 티 앞에서 바위만 찍고, 흰 벽 앞에서 가위만 찍으면 모델은 "어두우면 바위"를 배운다. 이게 진짜 혼동이고, 걱정이 맞아떨어지는 유일한 경우다.
    피하는 법은 간단하다. 배경 × 클래스를 격자로 채운다.
    밤색 티어두운 곳흰 벽합계

    한 조건에 2~3장만 넣는 것도 피한다. 너무 적으면 그 상황을 배우지도 못하면서 학습만 흔들린다. 한 조건당 스무 장쯤은 있어야 한다.

    어려운 사진을 test에 섞으면 시험이 어려워지므로 점수는 내려갈 수 있다. 그런데도 실사용은 좋아진다. 0.995는 쉬운 시험 점수였을 뿐이다.
    그래서 점수 대신 이걸 재야 한다 — 밤색 티 앞에서 10번 시도해 몇 번 맞는지. Before/After로 남기면 그 자체가 포트폴리오 근거가 된다.
    LabelImg 왼쪽의 PascalVOC / YOLO 버튼 — 둘 중 뭘로 해 놓아야 해?
    PascalVOC로 두면 된다. 그 버튼은 누를 때마다 둘을 오가는 토글이고, 지금 화면에 보이는 글자가 지금 저장될 형식이다. PascalVOC라고 보이면 그대로 두면 된다.
    버튼 표시저장되는 것이 프로젝트에서
    PascalVOC.xml — 클래스를 이름으로 적는다 (<name>scissors</name>)이걸 쓴다. 변환기가 이름으로 대조하므로 안전
    YOLO.txt — 클래스를 번호로 적는다 (0 0.5 0.5 0.3 0.4)쓰지 않는다. 아래 이유
    YOLO로 바로 저장하면 왜 위험한가
    txt에는 0, 1, 2라는 번호만 들어간다. 그 번호가 무엇을 뜻하는지는 LabelImg가 옆에 만드는 classes.txt의 줄 순서로 정해진다. 그 순서가 data.yaml(scissors=0, rock=1, paper=2)과 다르면 가위를 바위로 배운다. 오류도 경고도 없이 조용히 틀린다 — 학습이 다 끝나고 이상한 결과를 보고서야 안다.
    xml은 <name>scissors</name>처럼 이름을 그대로 적기 때문에 순서가 끼어들 여지가 없다.
    xml을 YOLO가 못 읽는 것은 맞다. 그래서 라벨링이 끝나면 Lec_python/2/데이터셋_확장/make_dataset.py로 한 번에 txt로 바꾼다. 순서는 xml로 라벨링 → 변환기 실행 → 학습이다.
    손 없이 배경만 찍는 것도 해야 해? 왜? 강사님 데이터에는 있었어, 없었어?

    그런데 정확히 말하면 — 모델이 배경을 아예 못 배운 건 아니다

    YOLO는 학습할 때 박스가 안 쳐진 자리는 전부 "여기엔 없다"로 밀어낸다. 그러니 보통 사진의 손 주변 여백에서도 배경을 배운다.
    문제는 그 여백에 무엇이 있었냐다. 82장의 여백에는 밝은 회색 벽밖에 없었다. 그래서 모델은 "밝은 벽 = 없다"만 배웠고, "얼굴 = 없다", "옷 = 없다", "가구 = 없다"는 배운 적이 없다. 그래서 얼굴이 나오면 손으로 잡는다.

    그래서 더 좋은 방법이 있다

    방법가르치는 것효율
    얼굴·상체가 같이 나온 사진에 손만 박스를 친다"이 손은 가위다" + "얼굴은 아무것도 아니다"가장 좋다. 한 장으로 둘을 가르치고, 실제 게임 장면과 똑같다
    손이 아예 없는 사진을 라벨 없이 넣는다 (background)"얼굴은 아무것도 아니다"좋다. 다만 손을 안 가르친다
    결론: 순수 배경 사진만 잔뜩 찍을 필요는 없다. 평소 게임하듯 얼굴·옷이 함께 나오게 찍고, 손에만 박스를 치는 것이 핵심이다. 여기에 손이 전혀 없는 사진을 전체의 10% 정도만 라벨 없이 섞으면 충분하다. (Ultralytics 문서도 background 사진 비율을 0~10%로 권한다.)
    자세가 비슷하든 말든 0.5초로 무작정 다 찍으면 안 돼? 스킵 기준이 러프하면 학습도 러프해지는 거 아냐?
    찍어도 된다. 다만 걱정하는 이유 때문은 아니고, 다른 두 가지 비용이 있다.

    먼저 걱정부터 — "미세한 차이를 못 배우는 것 아니냐"

    그렇지 않다. 건너뛴 프레임은 잘못 가르치는 것이 아니라 안 가르치는 것이다. 그리고 조금씩 기울어진 자세에 대한 내성은 거의 같은 사진을 여러 장 넣어서가 아니라 증강이 만들어 준다. 강사님 학습 명령의 degrees=15.0이 같은 사진을 매 epoch 마다 ±15도 안에서 무작위로 돌려 넣는다. 거의 똑같은 사진 두 장보다 증강 쪽이 훨씬 촘촘하다.

    진짜 비용 두 가지

    비용내용
    라벨링 시간사진 한 장마다 LabelImg로 손수 박스를 그려야 한다. 0.5초 무제한이면 1분에 120장이 쌓이는데, 상당수가 사실상 같은 그림이다. 이 프로젝트에서 진짜 한계는 촬영이 아니라 라벨링 시간이다.
    시험지 오염거의 같은 사진 두 장이 train과 test에 나뉘어 들어가면, 모델이 이미 본 것을 시험 보는 셈이 된다. mAP가 실제보다 높게 나오고 점수를 못 믿게 된다. 이게 더 큰 손해다.
    그래서 이렇게 바꿔 두었다: INTERVAL = 0.5, DIFF_TH = 3.0. 3.0은 카메라가 완전히 멈춰 있을 때 생기는 진짜 중복만 버리는 수준이라, 자세가 조금이라도 바뀌면 전부 저장된다. DIFF_TH = 0으로 두면 검사 자체를 안 한다. 끝날 때 몇 %를 버렸는지 출력하니 그 숫자를 보고 직접 조절하면 된다.
    프로젝트 결과는 mAP가 높을수록 좋게 평가되는 거 아냐?
    높으면 좋다. 그런데 "설명할 수 있는 수치"가 아니면 오히려 약점이 된다. 교수님 1기 피드백 자료에 이렇게 적혀 있다 —
    "자료에 적은 수치는 전부 설명할 수 있어야 한다. 설명 못 할 수치는 아예 넣지 않는 게 낫다."
    "'증강으로 왼손이 해결됐다'라고 쓰려면 수치가 필요하다."
    "결론 = 수치. 고찰 = 아직 안 되는 것(기울인 손, 다른 사람 손)."
    mAP는 내가 만든 시험지로 재는 점수다. 시험지를 쉽게 만들면 올라간다. "0.995입니다"라고 썼는데 "그럼 밤색 옷 앞에서는요?"라는 질문 하나에 무너지면 그 수치가 약점이 된다.

    그래서 점수를 잃지 않으면서 설명력을 얻는 방법 — 시험지를 둘로 나눈다

    시험지무엇쓰는 법
    val강사님 원본 22장 그대로. 한 장도 안 건드린다재학습 전후를 같은 시험지로 비교. 숫자가 비교 가능해진다
    test내가 찍은 어려운 사진 (밤색 티·어두운 곳·얼굴 포함)yolo val model=best.pt data=data.yaml split=test
    그러면 결과를 이렇게 두 줄로 쓸 수 있다.
    시험 조건Before (82장 학습)After (재학습)
    쉬운 조건 (강사님 22장)0.9950.99x — 떨어지지 않았다
    어려운 조건 (실사용)(측정)(측정) — 새로 생긴 능력
    한 줄짜리 0.995보다 훨씬 강하다. 높은 수치를 지키면서, 그 수치가 무엇을 뜻하는지 설명할 수 있고, 개선 과정까지 보여 준다. 교수님이 요구하는 "결론(수치) + 고찰(남은 것)" 구조가 저절로 나온다.
    make_dataset.py가 이 구조를 자동으로 만든다. 강사님 test 22장은 val로 그대로 두고, 새 사진 중 일부만 test_hard로 뺀다.

    1. 창을 아예 안 뜨게 (가장 좋다)오른쪽 위 Use default label 체크 + 옆 칸에 paper 입력. 박스를 그리면 묻지 않고 바로 그 라벨이 붙는다. 한 폴더가 한 클래스일 때 특히 좋다
    2. 드래그 방향을 바꾼다아래에서 위로 끌어 손끝(화면 위쪽)에서 마우스를 뗀다. 커서가 위에 있으니 창도 보이는 자리에 뜬다
    3. 안 보이는 채로 그냥 친다창은 열려 있고 입력 포커스도 거기 있다. 안 보여도 paper 타이핑 후 Enter를 누르면 그대로 들어간다
    라벨을 나중에 고치려면 오른쪽 Box Labels 목록에서 해당 줄을 두 번 클릭하면 된다. Use default label을 켜 둔 상태에서 한 손만 다른 클래스일 때(paper_rock 같은 폴더) 이 방법을 쓴다.
    손이 카메라에 너무 가까워서 화면 밖으로 잘린 사진 — 이런 건 라벨링 안 하는 게 낫나?
    한다. 잘린 물체는 검출 데이터셋에서 정상이다. 어느 데이터셋이든 화면 가장자리에 걸친 물체가 들어 있고, YOLO는 그걸 다루도록 만들어져 있다. 박스는 보이는 범위에만 치면 된다(화면 밖으로 연장하지 않는다).
    "안 하고 넘어간다"는 선택지가 아니다. 라벨 파일이 없는 사진은 YOLO가 "여기엔 아무것도 없다"로 배운다. 손이 둘이나 있는데 없다고 가르치게 되므로, 넣지 않느니만 못하다. 쓰지 않기로 했다면 파일을 폴더 밖으로 옮겨야 한다.

    판단 기준

    상황어떻게
    잘렸지만 사람이 보고 무슨 모양인지 안다라벨한다. 오히려 크기 다양성이 생겨 도움이 된다
    두 손이 겹쳤지만 둘 다 알아볼 수 있다둘 다 라벨한다. 박스가 겹치는 것은 정상이다
    사람이 봐도 손가락을 셀 수 없다 (95% 가려짐, 심한 흔들림·초점 나감)폴더 밖으로 옮긴다. 애매한 정답은 잡음이 된다
    다만 비율은 보자. 이런 초근접 사진이 전체의 30%를 넘으면 "손은 화면을 가득 채우는 것"으로 치우쳐 배운다. 몇 장 섞이는 것은 좋고, 대부분이 그러면 곤란하다. 실제 게임에서 손은 카메라에서 40~60cm에 있다.
    mAP50과 mAP50-95는 뭐라고 읽어? 그리고 둘의 차이가 아직 이해가 안 되는데
    읽는 법 : mAP는 "엠에이피" 또는 "맵"이라고 읽는다. mAP50은 "맵 오십", mAP50-95는 "맵 오십에서 구십오". 정식 이름은 mean Average Precision(평균 정밀도의 평균)이고, COCO 데이터셋에서 정한 국제 표준 지표라 어느 팀에서든 그대로 통한다.

    채점관 비유 — 이게 제일 빠르다

    사진 한 장에 손 하나가 있다. 정답 박스는 손을 딱 감싼 네모, 모델이 그린 박스는 살짝 어긋나 있다. 둘이 얼마나 겹치는지를 IoU라고 한다(0~1).
    채점 방식
    mAP50채점관이 한 명. "IoU가 0.50만 넘으면 맞은 걸로 쳐 준다"
    mAP50-95채점관이 열 명. 기준이 각각 0.50 / 0.55 / 0.60 / … / 0.95.
    열 명 점수의 평균이 최종 점수다

    숫자로 따라가 보자

    모델이 그린 박스가 정답과 IoU 0.70으로 겹쳤다고 하자.
    채점관 기준0.500.550.600.650.700.750.800.850.900.95
    판정OOOOOXXXXX
    mAP50 = 1.0 (첫 채점관만 보니까 통과)  /  mAP50-95 = 5/10 = 0.5 (열 명 평균)
    그래서 두 숫자를 같이 보면 이런 걸 알 수 있다.
    mAP50mAP50-95뜻
    높다높다잘 찾고, 박스도 정확하다
    높다낮다찾기는 다 찾는데 박스가 조금씩 어긋난다 ← 우리 경우
    낮다낮다아예 못 찾는다

    우리 숫자 해석

    새 사진 시험지에서 mAP50 0.975 / mAP50-95 0.619가 나왔다.
    → 손은 거의 다 찾아낸다(0.975). 다만 박스의 겹침 정도가 대략 0.7 언저리라 엄격한 채점관들에게서 점수를 잃는다.
    게임에는 영향이 적다. 박스가 몇 픽셀 어긋나도 좌/우 구분과 클래스는 그대로라 승패 판정은 똑같이 나온다. 그래서 "쓸 만하다"가 결론이고, "박스 정밀도는 아쉽다"가 고찰이다.
